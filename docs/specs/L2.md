# L2 - Detailed Requirements

Viewport classes: XS < 576px, SM >= 576px, MD >= 768px, LG >= 992px, XL >= 1200px.

Assumptions awaiting confirmation: a user may hold at most 200 tiles; the dashboard grid has 12 columns at widths of 1024px and above; the email sign-in link expires after 15 minutes; a session expires after 14 days idle or 30 days absolute.

---

## L2-001: Create a tile
**Traces to:** L1-001

A signed-in user shall be able to create a tile with a name, web address, description, colour and category. The new tile appears last in the user's order.

**Acceptance Criteria:**
1. Given a signed-in user, when they submit a valid tile, then the API returns 201 with the stored tile and its id.
2. Given a tile was created, when the dashboard is loaded, then the tile is shown after all existing tiles.
3. Given an unauthenticated request, when it posts a tile, then the API returns 401 and stores nothing.

---

## L2-002: Validate tile fields
**Traces to:** L1-001

Tile input shall be validated on the server and mirrored in the form.

**Acceptance Criteria:**
1. Given a tile with an empty name, when it is submitted, then the API returns 400 problem details naming the `name` field.
2. Given a name longer than 60 characters, when it is submitted, then the API returns 400 for `name`.
3. Given a description longer than 280 characters, when it is submitted, then the API returns 400 for `description`.
4. Given a colour that is not one of the allowed palette values, when it is submitted, then the API returns 400 for `colour`.
5. Given invalid input in the dialog form, when the user submits, then each invalid field shows an error linked to it with `aria-describedby` and focus moves to the first invalid field.

---

## L2-003: Restrict tile addresses
**Traces to:** L1-001

A tile address shall be an absolute `http` or `https` URL.

**Acceptance Criteria:**
1. Given an address `javascript:alert(1)`, when it is submitted, then the API returns 400 for `address`.
2. Given an address with scheme `data:` or `file:`, when it is submitted, then the API returns 400 for `address`.
3. Given an address `example.com` with no scheme, when it is submitted, then the API returns 400 for `address`.
4. Given an address longer than 2048 characters, when it is submitted, then the API returns 400 for `address`.
5. Given a valid `https://example.com/app` address, when it is submitted, then the tile is stored with the address unchanged.

---

## L2-004: Limit tiles per user
**Traces to:** L1-001

A user shall hold at most 200 tiles.

**Acceptance Criteria:**
1. Given a user with 200 tiles, when they create another, then the API returns 409 problem details and stores nothing.
2. Given a user with 199 tiles, when they create another, then the API returns 201.

---

## L2-005: View tiles
**Traces to:** L1-001

The API shall return the user's tiles in their saved order, and a single tile by id.

**Acceptance Criteria:**
1. Given a user with three tiles in a saved order, when they request the tile list, then the response lists all three in that order.
2. Given a tile id the user owns, when they request it, then the API returns 200 with that tile.
3. Given an id that does not exist, when it is requested, then the API returns 404 problem details.

---

## L2-006: Edit a tile
**Traces to:** L1-001

A user shall be able to change any tile field from an Edit dialog.

**Acceptance Criteria:**
1. Given an existing tile, when the user opens Edit, then the dialog shows the current values.
2. Given valid changes, when the user saves, then the API returns 200, the dashboard shows the new values, and the tile keeps its position.
3. Given invalid changes, when the user saves, then the dialog stays open, shows field errors, and nothing is stored.
4. Given the user cancels or presses Escape, when the dialog closes, then nothing changes and focus returns to the control that opened it.

---

## L2-007: Delete a tile
**Traces to:** L1-001

A user shall be able to delete a tile after confirming.

**Acceptance Criteria:**
1. Given an existing tile, when the user chooses Delete, then a confirmation dialog names the tile.
2. Given the user confirms, when the request completes, then the API returns 204, the tile disappears, and a toast confirms.
3. Given the user cancels, when the dialog closes, then the tile remains.
4. Given a tile was deleted, when the remaining tiles are loaded, then their relative order is unchanged.

---

## L2-008: Show tiles on the dashboard
**Traces to:** L1-002

The dashboard shall render every tile in the user's saved order, showing name, address host, description (on large tiles) and colour.

**Acceptance Criteria:**
1. Given a user with tiles, when they open the dashboard, then each tile appears once, in saved order.
2. Given a tile with a colour, when it renders, then the colour is applied through design tokens and text keeps AA contrast.

---

## L2-009: Tile placement and size
**Traces to:** L1-002

Each tile shall occupy a rectangle of cells on a 12-column grid, given by its column, row, column span and row span. A tile's size is its span; the default span for a new tile is 3 columns by 2 rows.

**Acceptance Criteria:**
1. Given a tile saved at column 0, row 0 with a span of 6 by 4, when the dashboard loads at 1280px, then the tile covers the first 6 columns and 4 rows.
2. Given a new tile with no placement, when it is created, then it takes a 3 by 2 span at the first free position in reading order (top row first, then left to right).
3. Given a saved layout, when the dashboard reloads, then every tile has the same position and span.

---

## L2-010: Empty dashboard
**Traces to:** L1-002

A user with no tiles shall see an empty state with a call to action.

**Acceptance Criteria:**
1. Given a user with no tiles, when they open the dashboard, then an empty state explains the dashboard and offers an "Add an app" button.
2. Given the user activates the button, when it is clicked, then the Add app dialog opens.

---

## L2-011: Loading and error states
**Traces to:** L1-002

The dashboard shall show a skeleton while loading and a retryable error if loading fails.

**Acceptance Criteria:**
1. Given the tile request is pending, when the dashboard renders, then skeleton tiles are shown and exposed as busy to assistive technology.
2. Given the tile request fails, when the dashboard renders, then an alert states the failure and offers Retry.
3. Given the user activates Retry, when the request succeeds, then the tiles replace the error.

---

## L2-012: Open an app in a new tab
**Traces to:** L1-003

Activating a tile shall open its address in a new browser tab without exposing ingresso to the opened page.

**Acceptance Criteria:**
1. Given a tile, when the user clicks or presses Enter on it, then its address opens in a new tab.
2. Given a tile link, when it renders, then it carries `target="_blank"` and `rel="noopener noreferrer"`.
3. Given the page is in edit mode, when the user clicks a tile, then the app does not open.

---

## L2-013: Record last opened
**Traces to:** L1-003

Opening a tile shall record the time on the server.

**Acceptance Criteria:**
1. Given a tile, when the user opens it, then the API stores the current UTC time as its last-opened time.
2. Given the record request fails, when the user opens a tile, then the app still opens and no error blocks the user.
3. Given a tile owned by another user, when its id is posted as opened, then the API returns 404 and changes nothing.

---

## L2-014: Show last opened
**Traces to:** L1-003

Each tile shall show when it was last opened, in relative terms.

**Acceptance Criteria:**
1. Given a tile opened 5 minutes ago, when it renders, then it shows "Opened 5 minutes ago".
2. Given a tile never opened, when it renders, then it shows "Never opened".
3. Given a tile, when it renders, then the exact timestamp is available as the element's accessible title.

---

## L2-015: Enter edit mode
**Traces to:** L1-004

The user shall be able to switch the dashboard into edit mode, which exposes drag handles and tile actions.

**Acceptance Criteria:**
1. Given the dashboard, when the user chooses "Edit layout", then each tile shows a drag handle and an Edit action (Delete is chosen inside the Edit dialog), and the page announces edit mode to assistive technology.
2. Given edit mode, when the user chooses Done, then handles and actions hide and tiles open apps again.

---

## L2-016: Move and resize with a pointer
**Traces to:** L1-004

In edit mode, the user shall be able to drag a tile to free cells and drag its corner handle to resize it. A destination that overlaps another tile shall be refused; other tiles never move.

**Acceptance Criteria:**
1. Given edit mode, when the user drags a tile, then a shadow shows the snapped destination cells and the tile follows the pointer.
2. Given the destination is free, when the user drops the tile, then it takes that position, the layout is saved, and no other tile moves.
3. Given the destination overlaps another tile, when the user drops the tile, then the shadow shows the refusal, the tile returns to its previous position, and nothing is saved.
4. Given edit mode, when the user drags a tile's resize handle into free cells, then its span changes and the layout is saved.
5. Given the save request fails, when a move or resize completes, then the previous layout is restored and an error toast is shown.
6. Given the user presses Escape during a drag, when the drag ends, then the tile returns to its previous position and nothing is saved.

---

## L2-017: Move and resize with the keyboard
**Traces to:** L1-004

Moving and resizing shall be possible without a pointer, with every change announced.

**Acceptance Criteria:**
1. Given a focused tile in edit mode, when the user presses an arrow key, then the tile moves one cell in that direction if the cells are free, and the new position is announced.
2. Given a focused tile in edit mode, when the user presses Shift and an arrow key, then the tile's span grows or shrinks by one cell if allowed, and the new size is announced.
3. Given a keyboard move into occupied cells or outside the grid, when it is attempted, then the tile stays put and the refusal is announced.
4. Given edit mode, when a tile receives focus, then instructions for the keys are available through its accessible description.

---

## L2-019: Reset the layout
**Traces to:** L1-004

The user shall be able to reset the layout to the default after confirming. The default layout packs tiles in creation order, oldest first, each at the default 3 by 2 span, in reading order.

**Acceptance Criteria:**
1. Given a rearranged dashboard, when the user chooses Reset layout, then a confirmation dialog explains that positions and sizes change and no tile is deleted.
2. Given the user confirms, when the request completes, then tiles are placed in creation order at 3 by 2, four per row, and no tile is deleted or edited.
3. Given the user cancels, when the dialog closes, then the layout is unchanged.

---

## L2-020: Leave edit mode safely
**Traces to:** L1-004

Edit mode shall not hold unsaved work.

**Acceptance Criteria:**
1. Given edit mode with a completed move or resize, when the user chooses Done, then no further save is needed and the saved layout matches what is shown.
2. Given edit mode, when the user navigates away and returns, then the dashboard opens in normal mode.

---

## L2-021: Open quick jump with `/`
**Traces to:** L1-005

Pressing `/` outside a text field shall open the search from any screen.

**Acceptance Criteria:**
1. Given focus is not in an input, when the user presses `/`, then the search opens focused and the key is not typed into it.
2. Given focus is in a text input, when the user presses `/`, then the character is typed and search does not open.
3. Given search is open, when the user presses Escape, then it closes and focus returns to where it was.

---

## L2-022: Filter tiles
**Traces to:** L1-005

Search shall filter tiles by name, address, category and description, case-insensitively.

**Acceptance Criteria:**
1. Given tiles named "Mail" and "Maps", when the user types "ma", then both are listed.
2. Given a tile in category "Work", when the user types "work", then it is listed.
3. Given text matching no tile, when it is typed, then a "No apps match" message is shown.
4. Given results change, when the list updates, then the result count is announced politely to assistive technology.

---

## L2-023: Open a match with Enter
**Traces to:** L1-005

Enter shall open the highlighted match.

**Acceptance Criteria:**
1. Given results, when the search opens, then the first result is highlighted.
2. Given a highlighted result, when the user presses Enter, then the app opens in a new tab and last-opened is recorded.
3. Given results, when the user presses Down or Up, then the highlight moves and wraps at the ends.
4. Given no results, when the user presses Enter, then nothing opens.

---

## L2-024: Browse the directory
**Traces to:** L1-006

A directory page shall list common apps.

**Acceptance Criteria:**
1. Given the Add app dialog, when the user chooses "Browse directory", then the directory lists apps with name, icon and description.
2. Given a search term typed in the directory, when results update, then only matching apps are listed.
3. Given an app already on the dashboard, when the directory renders, then it is listed with an "Added" mark in place of its Add button.

---

## L2-025: Add from the directory
**Traces to:** L1-006

Choosing a directory app shall prefill the tile form.

**Acceptance Criteria:**
1. Given a directory app, when the user chooses Add, then the form opens with its name, address, description and category filled in.
2. Given the prefilled form, when the user saves, then the tile is created at the first free 3 × 2 space, as when adding by address (L2-009).

---

## L2-026: Add by web address
**Traces to:** L1-006

The user shall be able to add any app by typing its address.

**Acceptance Criteria:**
1. Given the Add app dialog, when the user enters a valid address and a name, then the tile is created.
2. Given an address that fails L2-003, when the user submits, then the address field shows an error.
3. Given the address was already added, when the user submits it, then the form warns of the duplicate and lets the user continue or cancel.

---

## L2-027: Request a sign-in link
**Traces to:** L1-007

A user shall request a sign-in link by entering their email address.

**Acceptance Criteria:**
1. Given any well-formed email, when it is submitted, then the API returns 202 with the same message whether or not an account exists.
2. Given a malformed email, when it is submitted, then the API returns 400.
3. Given more than 5 requests for one address or 20 from one IP in an hour, when another arrives, then the API returns 429 with `Retry-After`, and the sign-in page says there were too many requests.
4. Given a link is issued, when it is stored, then only a hash of the token is persisted.
5. Given the API runs in Development (or the test host), when a link is issued, then it can be read from the dev mailbox at `/api/dev/mailbox`; in any other environment that endpoint does not exist, whatever the configuration.

---

## L2-028: Redeem a sign-in link
**Traces to:** L1-007

A sign-in link shall be single use and expire.

**Acceptance Criteria:**
1. Given a valid link, when it is redeemed, then a session is created and the user lands on the dashboard.
2. Given a link already redeemed, when it is used again, then the browser is sent to `/sign-in?link=used`, the page says the link was already used, and no session is created.
3. Given a link older than 15 minutes, when it is used, then the browser is sent to `/sign-in?link=expired`, the page says it expired, and the user can request a new one there.
4. Given a tampered or unknown token, when it is used, then the browser is sent to `/sign-in?link=invalid` and the page says only that the link did not work, without revealing why.

---

## L2-029: Verify email
**Traces to:** L1-007

A new account's email shall be verified before the dashboard opens.

**Acceptance Criteria:**
1. Given a first-time email, when the user redeems their link, then the email is marked verified.
2. Given an unverified account, when the user requests another verification email, then one is sent, subject to rate limiting.
3. Given an unverified account, when it calls a tile endpoint, then the API returns 403.

---

## L2-030: Secure server-side session
**Traces to:** L1-007

The session cookie shall be an opaque reference to a server-side session.

**Acceptance Criteria:**
1. Given a session is created, when the cookie is set, then it is `HttpOnly`, `Secure` and `SameSite=Lax`, and contains no user data.
2. Given a session idle for 14 days or older than 30 days, when it is used, then the API returns 401 and the session is removed.
3. Given an active session, when it is used, then its idle expiry is extended.
4. Given a session id the server does not know, when it is presented, then the API returns 401.

---

## L2-031: Sign out
**Traces to:** L1-007

The user shall be able to sign out from any screen.

**Acceptance Criteria:**
1. Given a signed-in user, when they choose Sign out, then the server session is deleted, the cookie is cleared, and they land on the sign-in screen.
2. Given a signed-out session id, when it is replayed, then the API returns 401.

---

## L2-032: Private dashboards
**Traces to:** L1-007

Each user's tiles shall be visible only to them.

**Acceptance Criteria:**
1. Given users A and B with tiles, when A lists tiles, then only A's tiles are returned.
2. Given B's tile id, when A requests, edits, deletes, lays out or marks it opened, then the API returns 404 and B's tile is unchanged.

---

## L2-033: Require authentication
**Traces to:** L1-008

Every endpoint except sign-in request, sign-in redemption and health shall require a valid session.

**Acceptance Criteria:**
1. Given no session, when any tile or account endpoint is called, then the API returns 401 problem details.
2. Given no session, when a page other than sign-in is opened, then the app redirects to sign-in.

---

## L2-034: CSRF protection
**Traces to:** L1-008

State-changing requests shall be protected against cross-site forgery.

**Acceptance Criteria:**
1. Given a valid session, when a POST, PUT or DELETE lacks the anti-forgery token, then the API returns 400 or 403 and changes nothing.
2. Given the app, when it sends a state-changing request, then it includes the token.

---

## L2-035: Security headers
**Traces to:** L1-008

Responses shall carry browser-hardening headers.

**Acceptance Criteria:**
1. Given any response, when headers are inspected, then `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy` and `Strict-Transport-Security` are present.
2. Given the CSP, when it is evaluated, then it permits no inline script and no third-party origins for fonts or scripts.

---

## L2-036: Rate limiting
**Traces to:** L1-008

The API shall rate limit by client.

**Acceptance Criteria:**
1. Given more than 300 API requests per minute from one session, when another arrives, then the API returns 429 with `Retry-After`.
2. Given normal use below the limit, when requests arrive, then none are limited.

---

## L2-037: Safe rendering of user content
**Traces to:** L1-008

Tile text shall always render as text, never as markup.

**Acceptance Criteria:**
1. Given a tile named `<img src=x onerror=alert(1)>`, when it renders, then the literal text is shown and no script runs.
2. Given a tile address containing quotes or angle brackets, when it renders, then the markup stays intact.

---

## L2-038: Privacy
**Traces to:** L1-008

The system shall not track users or log personal content.

**Acceptance Criteria:**
1. Given any page, when network requests are inspected, then none go to analytics or advertising hosts.
2. Given the logs, when a request is logged, then they contain no email address, token, cookie or tile address.
3. Given the user opens an app, when ingresso records it, then only the tile id and time are stored.

---

## L2-039: API response time
**Traces to:** L1-009

Tile endpoints shall respond quickly with up to 200 tiles.

**Acceptance Criteria:**
1. Given a user with 200 tiles, when the tile list is requested 100 times, then p95 latency is under 200 ms.
2. Given create, edit, delete and layout requests, when each is run 100 times against 200 tiles, then p95 latency is under 200 ms.

---

## L2-040: Dashboard load time
**Traces to:** L1-009

The dashboard shall become usable quickly.

**Acceptance Criteria:**
1. Given 200 tiles on a mid-range laptop over a simulated fast 4G connection, when the dashboard loads, then it is interactive in under 2 s.
2. Given the initial bundle, when it is built, then it loads no unused feature code on the dashboard route.

---

## L2-041: Responsive layout changes
**Traces to:** L1-009

Moves and resizes shall feel immediate.

**Acceptance Criteria:**
1. Given a completed drag, when the user drops or resizes a tile, then the new layout is shown within 100 ms, before the save finishes.
2. Given 200 tiles in edit mode, when the user drags a tile, then the drag preview keeps 60 frames per second on a mid-range laptop.

---

## L2-042: Responsive grid
**Traces to:** L1-010

The dashboard shall show the 12-column grid at widths of 1024px and above, and collapse to a flow list in reading order (top row first, then left to right) below that width. A width change never changes the saved layout.

**Acceptance Criteria:**
1. Given LG or XL width of at least 1024px, when the dashboard renders, then tiles keep their saved positions and spans on 12 columns.
2. Given a width from 768px to 1023px, when it renders, then tiles flow in two columns in reading order, and tiles spanning 6 or more columns take a full row.
3. Given a width below 768px, when it renders, then tiles show in one column in reading order.
4. Given the window narrows below 1024px and widens again, when the dashboard renders, then the saved layout is unchanged and no save request is sent.
5. Given any width, when it renders, then the page has no horizontal scroll.

---

## L2-043: Responsive dialogs and header
**Traces to:** L1-010

Dialogs and navigation shall fit small screens.

**Acceptance Criteria:**
1. Given XS width, when a dialog opens, then it fills the screen and its actions stay reachable.
2. Given XS width, when the header renders, then navigation collapses into a menu button.
3. Given a touch device, when controls render, then each touch target is at least 44 by 44 CSS pixels.

---

## L2-044: Themes
**Traces to:** L1-010

The app shall support light and dark themes.

**Acceptance Criteria:**
1. Given the system prefers dark, when the app loads, then the dark theme is applied.
2. Given the user picks a theme, when they reload, then that choice is kept.
3. Given either theme, when text is measured, then contrast meets WCAG 2.2 AA.

---

## L2-045: Keyboard and focus
**Traces to:** L1-010

Every function shall work with a keyboard, with a visible focus indicator.

**Acceptance Criteria:**
1. Given any screen, when the user tabs through it, then the order follows reading order and the focused control has a visible indicator.
2. Given any screen, when it loads, then a skip link to main content is the first focusable item.
3. Given a dialog, when it opens, then focus moves into it and is trapped; on close it returns to the opener.

---

## L2-046: Assistive technology
**Traces to:** L1-010

State changes shall be announced to assistive technology.

**Acceptance Criteria:**
1. Given a toast appears, when it renders, then it is announced through a live region.
2. Given every tile, when it renders, then its accessible name includes the app name and last-opened text.
3. Given `prefers-reduced-motion`, when the user moves tiles or opens dialogs, then animations are removed.

---

## L2-047: Request logging
**Traces to:** L1-011

Every request shall be logged with its final status.

**Acceptance Criteria:**
1. Given a request that throws a handled exception, when it completes, then the log shows the handled status code (for example 404), not 500.
2. Given any request, when it is logged, then the entry includes method, path, status, duration and a correlation id.

---

## L2-048: Problem details
**Traces to:** L1-011

Errors shall be returned as RFC 7807 problem details.

**Acceptance Criteria:**
1. Given a validation failure, when the API responds, then the body has `application/problem+json`, status 400 and per-field errors.
2. Given an unhandled exception, when the API responds, then it returns 500 problem details with a correlation id and no stack trace.

---

## L2-049: CLI migrate, seed and reset
**Traces to:** L1-011

The CLI shall manage the database.

**Acceptance Criteria:**
1. Given an empty database, when `migrate` runs, then the schema is created and the exit code is 0.
2. Given a migrated database, when `seed` runs twice, then the second run adds nothing and succeeds.
3. Given a database with data, when `reset` runs, then data is removed and the schema is recreated, and the command requires an explicit confirmation flag.
4. Given a failure, when any command runs, then it exits non-zero with a message.

---

## L2-050: No migrations on startup
**Traces to:** L1-011

The API shall never change the schema when it starts.

**Acceptance Criteria:**
1. Given a database that lacks pending migrations, when the API starts, then it makes no schema change.
2. Given a database with pending migrations, when the API starts, then it does not apply them and logs a warning.

---

## L2-051: Tile size limits
**Traces to:** L1-004

A tile's span shall stay within 2 to 12 columns and 1 to 8 rows, and inside the grid's 12 columns.

**Acceptance Criteria:**
1. Given a tile 2 columns wide, when the user tries to shrink it, then it stays 2 columns wide and the limit is announced.
2. Given a tile at column 9 with a span of 3, when the user tries to widen it, then it stays 3 columns wide.
3. Given a layout request with a span outside the limits, when it is submitted, then the API returns 400.

---

## L2-052: Save the layout
**Traces to:** L1-004

The layout shall be saved as one request listing every tile's column, row and span.

**Acceptance Criteria:**
1. Given a valid layout for all of the user's tiles, when it is sent to `PUT /api/tiles/layout`, then the API returns 200 and stores every position and span.
2. Given a layout that omits a tile, repeats a tile, or includes another user's tile, when it is sent, then the API returns 400 and nothing changes.
3. Given a layout where two tiles overlap or a tile extends past column 12, when it is sent, then the API returns 400 and nothing changes.

---

## L2-053: Repair a stored layout
**Traces to:** L1-002

A stored layout that is invalid shall be repaired on display by the same rules every time, without losing a tile.

**Acceptance Criteria:**
1. Given two stored tiles that overlap, when the dashboard loads, then the later tile in reading order moves to the first free position and both are shown.
2. Given a stored tile that extends past column 12, when the dashboard loads, then it is moved or narrowed to fit.
3. Given the same invalid layout, when it is repaired twice, then the result is identical.

---

## L2-054: Edit layout needs a wide window
**Traces to:** L1-004

Edit mode shall be available only at widths of 1024px and above.

**Acceptance Criteria:**
1. Given a width below 1024px, when the user views the dashboard, then the Edit layout control is disabled with an explanation that a wider window is needed.
2. Given edit mode at 1280px, when the window narrows below 1024px, then edit mode ends and the layout bar is removed.

---

## L2-087: Register an app for sign-in
**Traces to:** L1-012

The CLI shall register an app the owner publishes as a public client that signs in with PKCE.

**Acceptance Criteria:**
1. Given a name and a redirect address, when `clients add --name <name> --redirect-uri <address>` runs, then the app is registered as a public client that must use PKCE, and the CLI prints its client ID and exits 0.
2. Given one or more `--post-logout-redirect-uri` addresses, when `clients add` runs with them, then they are stored with the app as its sign-out return addresses.
3. Given a name already registered, ignoring case, when `clients add` runs with it, then nothing is registered and the CLI exits 1 saying the name is taken.

---

## L2-088: Client address rules
**Traces to:** L1-012, L1-008

A client's redirect and sign-out return addresses shall be exact, absolute and safe.

**Acceptance Criteria:**
1. Given an address that is not absolute, or that uses a scheme other than `https` (`http` is allowed only for `localhost`, `127.0.0.1` and `[::1]`), when `clients add` runs, then nothing is registered and the CLI exits 1 naming the address.
2. Given an address with a fragment or a `*` wildcard, when `clients add` runs, then nothing is registered and the CLI exits 1 naming the address.
3. Given no redirect address, an empty name or a name over 100 characters, when `clients add` runs, then nothing is registered and the CLI exits 1 with the reason.

---

## L2-089: List and remove registered apps
**Traces to:** L1-012

The CLI shall list registered apps and remove one by client ID.

**Acceptance Criteria:**
1. Given registered apps, when `clients list` runs, then each app's name, client ID, redirect addresses and sign-out return addresses are printed, ordered by name.
2. Given no registered apps, when `clients list` runs, then it prints that no apps are registered and exits 0.
3. Given a registered client ID, when `clients remove --client-id <id>` runs, then the app is removed and the CLI prints its name.
4. Given an unknown client ID, when `clients remove` runs, then nothing changes and the CLI exits 1 saying no app has that client ID.

## L2-090: Registrations survive migrate and seed
**Traces to:** L1-012, L1-011

App registrations shall be stored in the database through the OpenID Connect server's stores and kept by the maintenance commands.

**Acceptance Criteria:**
1. Given an empty SQLite or SQL Server database, when `migrate` runs, then the client tables exist and no migration is pending (refines L2-049).
2. Given registered apps, when `seed` runs again, then they are unchanged.

## L2-091: Discovery and signing keys
**Traces to:** L1-012

ingresso shall publish its OpenID Connect discovery document and public signing keys.

**Acceptance Criteria:**
1. Given anyone, when they request `/.well-known/openid-configuration`, then it returns the issuer (the public base URL), the authorization, token and JWKS addresses, `code` as the only response type, and `S256` as the only code challenge method.
2. Given anyone, when they request the JWKS address, then it returns at least one public signing key and no private key material.

## L2-092: Sign in to an app with a session
**Traces to:** L1-012

A person with an ingresso session shall sign in to a registered app without seeing ingresso.

**Acceptance Criteria:**
1. Given a signed-in person with a verified email and a registered app, when the app sends an authorization request with an exactly registered redirect address, response type `code` and an `S256` code challenge, then the browser returns to that address with a code and the app's `state`.
2. Given that code and its verifier, when the app calls the token endpoint, then it receives an ID token signed by a key in the JWKS, issued by ingresso for the app's client ID, with the person's id as `sub`, their email as `email`, and the app's `nonce`.
3. Given a code already exchanged, or a wrong verifier, when the app calls the token endpoint, then it receives `invalid_grant` and no tokens.
4. Given an authorization request without a code challenge, or with the `plain` method, when it is sent, then no code is issued.

## L2-093: Sign in to an app without a session
**Traces to:** L1-012, L1-007

A person without an ingresso session shall sign in by email link and return to the app.

**Acceptance Criteria:**
1. Given no session, when an app sends an authorization request, then the browser goes to `/sign-in` with the request as its return address, and the page names the app.
2. Given that page, when the person requests a link and opens it, then a session starts and the browser continues the authorization request back to the app with a code (refines L2-027 and L2-028).
3. Given a signed-in person whose email is not verified, when an app sends an authorization request, then no code is issued and the browser goes to `/verify-email` (refines L2-029).

## L2-094: Unknown app or address
**Traces to:** L1-012, L1-008

An authorization request ingresso cannot trust shall never redirect.

**Acceptance Criteria:**
1. Given an unknown client ID, or a redirect address that does not exactly match one registered for the app, when the authorization request is sent, then the browser goes to `/authorize-error` and is never sent to the given address.
2. Given `/authorize-error`, when it is shown, then it says the app can't sign in with ingresso and offers a way to the person's apps.

## L2-095: Register an API and its scopes
**Traces to:** L1-012

The CLI shall register an API the owner publishes, with the scopes apps may ask for to call it.

**Acceptance Criteria:**
1. Given a name, an audience and one or more scopes, when `resources add --name <name> --audience <audience> --scope <scope>` runs, then the API is registered with those scopes, and the CLI prints its name, audience and scopes and exits 0.
2. Given an audience or a scope already registered, an empty name, no scope, a value containing spaces, or a reserved scope (`openid`, `email`, `profile`, `offline_access`), when `resources add` runs, then nothing is registered and the CLI exits 1 with the reason.
3. Given registered APIs, when `resources list` runs, then each API's name, audience and scopes are printed, ordered by name; with none, it prints that no APIs are registered.
4. Given a registered audience, when `resources remove --audience <audience>` runs, then the API and its scopes are removed and the CLI prints its name; given an unknown audience, nothing changes and the CLI exits 1.

## L2-096: Allowed scopes per app
**Traces to:** L1-012, L1-008

An app shall get access tokens only for the API scopes it is allowed.

**Acceptance Criteria:**
1. Given a registered API scope, when `clients add ... --scope <scope>` runs, then the app is allowed that scope, and `clients list` shows it.
2. Given a scope no API has, when `clients add ... --scope <scope>` runs, then nothing is registered and the CLI exits 1 naming the scope.
3. Given an app that is not allowed a scope, when it sends an authorization request asking for that scope, then the browser returns to the app with `invalid_scope` and no code.

---

## L2-097: Access tokens
**Traces to:** L1-012

The token endpoint shall issue an access token for the APIs whose scopes the app was granted.

**Acceptance Criteria:**
1. Given a code issued for an allowed API scope, when the app exchanges it, then it receives an access token as a JSON Web Token signed by a key in the JWKS (not encrypted), with the person's id as `sub`, the API's audience as `aud`, the granted scopes in `scope`, and an `exp`.
2. Given no configured lifetime, when an access token is issued, then it expires 10 minutes after it was issued; given `IdentityProvider:AccessTokenLifetime`, it expires after that lifetime.

---

## L2-098: An API validates access tokens
**Traces to:** L1-012, L1-008

An app's API that validates tokens against ingresso's discovery document shall accept only valid tokens issued for it.

**Acceptance Criteria:**
1. Given an API that validates bearer tokens for its audience against ingresso's discovery document, when it is called with an access token ingresso issued for that audience, then it answers with the caller's identity.
2. Given that API, when it is called with an expired token, a token whose signature was altered, or a token issued for another audience, then it answers 401.
3. Given the sample app signed in through ingresso, when it shows its home page, then it shows data from its own API, fetched with the person's access token.
